## Bottom line

The Slack thread’s progression is sound:

`AI factories → loop engineering → graph engineering`

But graph engineering is not the factory.

- Loop engineering governs one adaptive agent loop.
- Graph engineering composes loops, tools, deterministic checks, routing, parallel work, retries, and human gates.
- AI-factory engineering operates those graphs safely across durability, identity, evaluation, cost, versioning, governance, and release.

The core thesis is:

> The graph is the process topology. It is not the factory.

## Current state

“Graph engineering” is a very new label for an established architectural pattern. LangChain publicly framed the term on July 22, while acknowledging that graph-based agent orchestration has existed for years. Google ADK 2.0 has moved graph-first, AutoGen’s GraphFlow remains experimental, and OpenAI explicitly warns that declarative graphs become cumbersome as workflows grow dynamic and complex. [LangChain](https://www.langchain.com/blog/3-years-of-graph-engineering-with-langgraph), [Google ADK](https://developers.googleblog.com/announcing-adk-go-20/), [OpenAI](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)

There is currently:

- no shared definition of graph engineering;
- no portable cross-framework graph format;
- no standard checkpoint, reducer, replay, migration, or evaluation contract;
- substantial ambiguity with knowledge graphs, context graphs, lineage graphs, and model computation graphs.

The Slack sequence most plausibly means control-flow/stateful execution graphs, not knowledge graphs. The latter should remain a secondary topic because the AI Engineer ecosystem already treats “Graphs,” “Software Factories,” and “AI Factories” as separate territories.

## Architectural and scale limitations

The major problems are:

- **Topology is not semantics.** A deterministic edge can still lead to a nondeterministic model, stale context, an unsafe tool call, or an incorrect patch.
- **Execution graphs and information-flow graphs differ.** AutoGen, for example, separates its execution graph from its message graph. Controlling who runs next does not automatically control who sees which context.
- **Durability changes application semantics.** Resume and replay can re-execute model calls and external actions. Side effects require durable intent, idempotency keys, receipts, deduplication, and sometimes compensation.
- **Parallelism creates merge problems.** Fan-out introduces checkpoint conflicts, state reducers, conflicting patches, partial success, cancellation, and rate-limit pressure. Coding work is also less naturally parallel than research.
- **Static diagrams stop matching runtime reality.** Dynamic workers, model-selected routes, cycles, nested graphs, and late-bound tools make visual comprehensibility and exhaustive path testing difficult.
- **Observability is not evaluation.** A trace shows what ran; it does not prove that the route was justified, the patch was correct, or the workflow was economical.
- **Security extends through every node.** An allowed edge is not authorization. Persistent state and cross-tool execution add prompt injection, confused-deputy, credential, provenance, and secret-retention risks.
- **Human approval can become stale.** A paused graph may resume after the repository, policy, model, or target action has changed.
- **Costs are topology-dependent and stochastic.** Anthropic reports roughly 15× chat token usage in its multi-agent research workload and specifically notes that coding offers fewer truly parallelizable tasks. [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Live-run versioning is hard.** Graph topology, state schemas, prompts, models, tools, policies, and evaluators can all change while checkpoints remain active.
- **MCP and A2A do not solve graph portability.** They standardize capability access and agent communication, not internal orchestration or recovery semantics.

A stronger formulation is:

> **The Graph Is Not the Factory: A Reference Architecture for Production Coding Agents**

The organizing pattern should be:

`failure → architectural control → proof that the control works`

For example:

1. **Retries duplicate external actions**

   Solution: durable intent records, stable idempotency keys, tool receipts, deduplication, and compensation paths.

   Proof: crash immediately after creating a branch or PR, resume the graph, and show that the external action occurs only once.

2. **Parallel agents create conflicting state and patches**

   Solution: isolated workspaces, typed state reducers, explicit artifact ownership, deterministic joins, and conflict escalation.

   Proof: run two agents against overlapping files and demonstrate safe merge, rejection, or human escalation.

3. **Approvals become stale**

   Solution: bind approval to the exact artifact hash, repository revision, policy version, proposed action, and expiry.

   Proof: change the repository after approval and show that execution fails closed rather than applying the stale decision.

4. **Graph replay is not reproducible**

   Solution: a run manifest pinning the graph, state schema, prompt, model, tool contract, policy, and evaluator versions.

   Proof: resume an old checkpoint after deploying a new graph and demonstrate controlled migration or quarantine.

5. **An allowed edge becomes an authorization bypass**

   Solution: per-node workload identity, least-privilege capabilities, trusted state labels, sandboxing, and action-scoped authorization.

   Proof: inject a manipulated tool description or credential-scope mismatch and show the policy layer denying it.

6. **Traces show activity but not correctness**

   Solution: connect execution traces to node, transition, trajectory, outcome, and policy evaluations.

   Proof: show a graph that completes successfully but fails its artifact or trajectory invariant.

7. **Fan-out destroys the economics**

   Solution: branch-level token, tool, retry, concurrency, and latency budgets with admission control and early termination.

   Proof: compare unrestricted fan-out with budgeted execution using quality, latency, and cost measurements.

For a 15–20 minute talk, I would not give all seven equal time. Use three failures as live or recorded demonstrations—duplicate side effects, conflicting parallel edits, and stale approval—then show how the seven controls fit into one reference architecture.

The audience should leave with three reusable artifacts:

- a production reference architecture;
- a failure-injection matrix;
- a run-manifest and evidence contract.

The proposal’s central promise becomes:

> I will take a plausible coding-agent graph, break it in production-relevant ways, then rebuild it with durability, side-effect safety, isolation, authorization, evaluation, budgets, and lifecycle controls. The result is a practical definition of what turns an agent graph into an AI software factory.

That is much more acceptance-worthy: it has a problem, an implementable solution, empirical proof, and something attendees can apply to their own systems.

## ThreadLoop: the outer work graph

ThreadLoop is already a concrete answer to “graph topology is not enough.”

Its lifecycle is an explicit cyclic state graph:

`queued → framed → proof_ready → implementing → verifying → reviewing ↔ repairing → ready_for_human → completed`

But the edge alone never authorizes advancement. Each transition is guarded by plans, current-HEAD proof, repair budgets, review state, approval and merge observations. [Lifecycle graph](~/Code/threadloop/docs/lifecycle.md:3)

It contributes:

- persistent SQLite lifecycle state;
- expected state versions and idempotency keys;
- atomic transition, audit and idempotency records;
- immutable receipts that become stale after a new commit;
- bounded repair re-entry;
- signed, identity-bound CI and review evidence;
- same-HEAD human approval and merge requirements for completion;
- separation between lifecycle authority and telemetry. [Transition transaction](~/Code/threadloop/docs/lifecycle.md:51), [transition authorities](~/Code/threadloop/docs/lifecycle.md:56), [telemetry boundary](~/Code/threadloop/docs/observability.md:67)

ThreadLoop is therefore closer to a proof-carrying workflow controller than an agent framework. It does not decide how an agent reasons, dynamically schedule arbitrary graph nodes, or govern every tool action inside implementation. The caller executes work; ThreadLoop determines whether the resulting evidence authorizes advancement.

## The combined architecture

A credible integration would work like this:

1. ThreadLoop creates the immutable task and proof plan.
2. It authorizes entry into `implementing`.
3. The governed harness executes the coding run under the five gates.
4. The harness emits a receipt bound to the plan, capability set, budget, patch and workspace digest.
5. A signing adapter wraps that receipt with ThreadLoop’s session, gate, repository, branch and HEAD identities.
6. ThreadLoop imports and verifies it without automatically advancing state.
7. An explicit transition revalidates the current repository and evidence.
8. Independent review, repair and same-HEAD human approval remain outside the implementing agent’s authority.

There is no direct code dependency between the two local repositories today, and their receipt formats are not currently compatible. That is useful: the integration is a real research contribution, not something to imply already exists.

## Canonical Contracts

Wake invariant:

````markdown
## Canonical Contracts

### Runner skill contract

Each Codex wake:

1. Receives the four explicit inputs.
2. Validates the canonical repository root, named branch, HEAD, clean worktree, protocol version, explicit session, audit status, and repair budget.
3. Reads `session next`.
4. Performs at most one authorized action:
   - one executable lifecycle transition;
   - one bounded `COMMIT_IMPLEMENTATION` or `COMMIT_REPAIR` action;
   - one stored local gate; or
   - no mutation and a handoff.
5. Stops after that action or handoff.

The skill is the runner. No extracted TypeScript controller sits between Codex and the existing ThreadLoop CLI in this pilot.

### Operator-retained wake handoff

Before a transition or other side effect, the operator retains the fields the skill requires:

session_id
wake_id
mode
branch
head_sha
worktree_clean
lifecycle_state
lifecycle_state_version
selected_action
action_started
action_outcome
action_result
transition_request
stop_reason
next_authority
```

The record may be maintained as one append-only local JSONL file. It is needed for honest duplicate/crash handling, but it does not require new runtime code.

### Coding-agent action

During `COMMIT_IMPLEMENTATION`, Codex may:

- Read the task, rules, and plan.
- Write failing behavior tests.
- Implement the smallest feature.
- Run focused non-ThreadLoop checks.
- Create at most one scoped commit.

It must leave a clean worktree and stop. It must not run a ThreadLoop gate, transition, evidence import, push, or PR action in the same wake.

`COMMIT_REPAIR` follows the same boundary and is limited to the complete current blocking finding set.

### External evidence handoff

The runner stops when signed CI or review evidence is required. The operator:

1. Invokes the exact pinned caller workflow.
2. Downloads the exact package for the current feature HEAD.
3. Imports it using the explicit session.
4. Records the result in the wake handoff.
5. Starts a later wake with a new `wake_id`.

These are supervised pilot operations, not runner behavior.

### Human stop

At `ready_for_human`, `blocked`, `completed`, or exhausted repair budget, Codex starts no new action. The pilot ends at `ready_for_human` without approval or merge.

## TDD And BDD Implementation Strategy

The feature wake begins with these red scenarios:

1. Authorized payment + new key -> one capture and one event.
2. Same key retry -> identical response and no second event.
3. Captured payment + new key -> conflict, no mutation, no event.
4. Pending payment + new key -> conflict, no mutation, no event.
5. Missing scope or idempotency key -> existing fail-closed behavior remains.

Only after the targeted tests demonstrate the gap does Codex modify `src/signalpay_api/app.py`. It then reruns the focused tests and creates one feature commit.

Full `make verify` is not bundled into the implementation action. ThreadLoop runs it later as the stored local gate while the repository is clean and committed.

If review produces a legitimate blocker, a later repair wake begins from a test or reproduction for that finding, applies the smallest correction, and creates one repair commit. All local and signed evidence must then be refreshed for the repair HEAD.

The pilot deliberately starts at least one verification, review, or repair wake in a fresh Codex context. The new context receives only the repository, the runner skill, and the four explicit inputs.

## Component Design

The pilot uses the existing architecture:

```text
operator or scheduled task
  -> four explicit wake inputs
  -> Codex reads runner skill
  -> existing ThreadLoop CLI projection
  -> one Codex action or one handoff
  -> operator records outcome
  -> later independent wake
```

ThreadLoop owns lifecycle truth, proof plans, receipts, review evidence, repair budget, guarded transitions, and audit persistence.

The runner skill owns the procedure for one wake. Codex owns the bounded code change. The operator owns wake delivery and the local handoff record. GitHub Actions owns signed sensor execution. The human owns irreversible authority.

The pilot is testing whether this division is usable. Adding a software controller before running the pilot would hide the coordination friction the experiment needs to reveal.

## Failure And Recovery Rules

- Missing or invalid wake input -> run no ThreadLoop command; operator corrects the invocation.
- Dirty worktree before a wake -> preserve it exactly and stop; never clean, reset, stash, or repeat work automatically.
- Branch, HEAD, repository, session, or protocol mismatch -> stop and record the observed facts.
- Ambiguous transition response -> reuse the same wake ID and exact retained request only after revalidating the Git snapshot.
- `STATE_VERSION_CONFLICT` or `IDEMPOTENCY_CONFLICT` -> stop; do not mint a new key in the same wake.
- Crash during repository work -> preserve the worktree and mark the handoff outcome unknown; a human inspects before any later action.
- Uncertain local gate outcome -> do not replay it as a duplicate.
- Missing, stale, or corrupt proof -> remain in the current state and follow the exact required-work handoff.
- Signed package collection/import failure -> retain the current lifecycle state and exact error; retry only under operator supervision.
- Blocking review finding -> enter repair only through the executable reviewing-to-repairing transition and within budget.
- Clean review -> do not invent a defect to exercise repair.
- Fresh Codex context cannot continue -> record a failed usability criterion; do not compensate with hidden transcript context.
- Unknown required-work code -> fail closed and hand it to the operator.
- `ready_for_human`, blocked state, exhausted budget, approval, or merge requirement -> stop for human authority.
````
